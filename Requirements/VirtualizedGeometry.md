# Unity向けNanite相当・仮想化ジオメトリツールの開発指示

あなたはUnityの描画基盤、GPU駆動レンダリング、メッシュ処理、
ストリーミングを担当するエンジニアです。

現在のワークスペースに、Unity用の独立した仮想化ジオメトリ
パッケージを設計・実装・検証してください。

設計書だけ、疑似コードだけ、LODGroupの自動生成だけで終わらず、
実際に動く変換ツールとランタイム描画を作ってください。


## 1. 到達目標

高密度の静的メッシュを専用データへ変換し、
画面に必要な細かさだけをGPUで選択・描画する。

元データ全体をGPUメモリに常駐させず、
必要なジオメトリページを非同期に読み込む。

利用者の操作は、次を基本とする。

「メッシュを選ぶ → Convert → 専用Rendererを配置
 → 通常どおりシーンを操作する」

手作業によるLOD作成を要求せず、
巨大な単一メッシュの内部でも、
場所ごとに異なる詳細度を選択できるようにする。

不足する地形ディテールの生成、テクスチャの仮想化、GIは
別機能とし、本ツールの完成条件へ混ぜない。

これはUnreal Engineのコードや内部アセット形式を
Unityへ移植する作業ではない。

公開資料と利用条件を確認したライブラリを用いた独立実装とし、
仮称をVirtualized Geometryとする。

Epicの公式製品、完全互換実装、同等性能を検証済みであるかの
ように表記しない。


## 2. 最初に実環境を確認する

AGENTS.mdなどの作業規約、Git差分、ProjectVersion.txt、
manifest.json、packages-lock.json、Renderer設定、
既存テストを確認する。

UnityとURPの正確なバージョン、利用可能なGraphics API、
GPU機能を記録する。

第一ターゲットは次とする。

- Unity 6系
- URP
- Windows Standalone
- DirectX 12

既存プロジェクトがある場合はそのバージョンを優先し、
UnityやURPを無断更新しない。

正確なAPIはインストール済みパッケージと
該当バージョンの公式資料で確認し、
存在しないAPIを想像で書かない。

標準バックエンドは、
Compute Shader、GPUバッファ、間接描画、
通常のハードウェアラスタライズで成立させる。

Mesh Shader、64bit GPU atomic、bindless、
ネイティブ描画プラグインを初期必須条件にしない。

実機で利用可能と確認した高度機能だけ、
別バックエンドとして後から追加する。

ECS/DOTSは必須にしない。
必要性が測定できた部分だけ採用する。

既存の描画基盤、Omni、シーン、入力、カメラ操作を
無関係に改造しない。


## 3. 対応範囲と完成の区別

v0.1の必須範囲は次とする。

- 静的な頂点形状の三角形メッシュ
- 不透明マテリアル
- インスタンス化
- GPUクラスタLOD
- GPUカリング
- ページストリーミング
- URP描画
- 変換Editor UI
- テストとベンチマーク

頂点形状が静的でも、
オブジェクトの移動・回転・スケール変更には対応する。

非一様スケールと負スケールを正しく扱えない処理は、
診断を出して安全な描画経路に切り替える。

最初の描画対象は、
URP Forward、単一のBase Camera、MSAAなしとする。

その後、Game ViewとScene Viewの同時利用、
複数の独立Base Cameraを検証する。

Camera Stack、XR、Deferred、HDRP、Built-in、WebGPU、
モバイル、SkinnedMesh、透過、任意の頂点変形は
後続対応とし、未対応を明示する。

これは本ツールの開発順序であり、
UE側Naniteの対応範囲を説明するものではない。

v0.2以降の目標は次とする。

- Visibility Buffer
- 微小三角形のソフトウェアラスタライズ
- ハードウェアとのハイブリッド描画
- 本ジオメトリからの直接の影描画
- 対応プラットフォーム拡大

初期段階を完成させるために後回しにしてよいが、
未実装のまま「Nanite完全再現」と報告しない。


## 4. パッケージ構造

原則としてUPMパッケージ化し、
Editor、Runtime、Shaders、Tests、Samples、
Documentationを分離する。

責務は次を目安にし、
既存構成に合わせて名前は調整してよい。

Importer / Builder：
入力検証、クラスタ化、階層構築、簡略化、ページ生成。

MeshAsset / Instance：
変換済みデータの参照と個別インスタンス情報。

PageStore / StreamingManager：
非同期I/O、CPUキャッシュ、GPU常駐管理。

RendererFeature / RenderPass：
GPU選択、描画、URPとの接続。

Debugger / Benchmark：
可視化、計測、再現テスト。

元のMeshを破壊せず、新しい変換済みアセットを生成する。

変換設定、元アセットGUID、内容ハッシュ、
ビルダーのバージョンでキャッシュを管理する。

バイナリ形式には、
バージョン、サイズ、オフセット、整合性検証情報を持たせる。

C#とHLSL間の構造体サイズ、アラインメント、
インデックス範囲をテストする。


## 5. オフライン変換・クラスタ階層

まず入力の以下を検査する。

縮退三角形、不正インデックス、NaN、重複、
開いた境界、非多様体、UVシーム、
法線・マテリアル境界。

修復できない入力は理由付きで拒否するか、
変換前のRendererにフォールバックさせる。

近接する三角形を小さなクラスタに分ける。

初期候補は最大64～128三角形程度とし、
頂点数制約と描画効率を測定して決める。

クラスタごとに、
頂点・三角形参照、境界、幾何誤差、
マテリアル情報、ページ参照を保持する。

階層は、次を基本候補とする。

近接クラスタのグループ化
→ グループ境界を考慮した簡略化
→ 再クラスタ化
→ 上位階層の生成

meshoptimizer等の利用を検討し、
クラスタ化、簡略化、圧縮を
必要以上に一から再発明しない。

ただし、そのライブラリを呼ぶだけで
階層LODやストリーミングまで完成したことにはしない。

依存バージョン、ライセンス、ビルド手順、
Editor用とPlayer用の必要物を記録する。

独立した各クラスタを勝手に簡略化して切り替える方式は、
正しさを確認できない限り採用しない。

隣接クラスタと異なるLODの接続を保つ仕組みを設計する。

階層がDAGになる場合は、
単純な親子ツリーだと仮定せず、
置換グループ、依存関係、
選択可能な組み合わせを明示する。

必須不変条件：

- 選択されたLOD集合が対象領域を過不足なく覆う。
- 親の粗い表現と、それが置き換える細かい表現を
  重複描画しない。
- 置換グループの必要データがそろうまで
  部分的に切り替えない。
- 境界に新しい亀裂、穴、誤ったT-junctionを作らない。
- 共有頂点はクラスタごとの量子化差でずれない。
- 簡略化できない入力でも無限ループせず、
  正しい停止・保持・診断を行う。

連結関係と描画属性を分けて扱い、
同じ位置にあるUVシーム頂点などを不適切に溶接しない。

単なる誤差ペナルティで境界保持を保証したことにせず、
採用方式の根拠と検証を用意する。

頂点数削減率だけで品質を判定せず、
細い形状、シルエット、穴、法線、UVも検証する。


## 6. 画面誤差に基づくLOD選択

カメラとの距離だけでLODを決めず、
幾何誤差を画面上のピクセル誤差へ変換して選択する。

解像度、FOV、投影方式、物体スケール、
境界の奥行き、near planeとの交差を扱う。

簡略化器の誤差値が何を意味するか確認する。

QEMのコスト、相対誤差、長さの誤差、
実測値、保守上界を混同しない。

量子化誤差と階層の累積誤差も考慮し、
上位階層ほど誤差が過小評価されないようにする。

通常時は、設定したピクセル誤差を満たす
最も粗い有効表現を選ぶ。

カメラが境界内部にある場合や
near planeをまたぐ場合は、
危険な除算や過小評価を避ける。

高速移動や閾値付近でLODが往復しないように
ヒステリシスを導入する。

ページ未到着・メモリ予算不足では
粗い常駐表現を描き続ける。

その場合は品質目標未達として計測し、
ピクセル誤差を満たしたと偽らない。

CPUの参照選択器を小規模テスト用に作ってよい。

本番のクラスタ選択はGPUで行い、
参照実装との比較に使う。


## 7. GPU選択と間接描画

GPUで階層走査、LOD選択、Frustum Culling、
可視リスト圧縮、描画引数生成を行う。

Normal Cone Cullingは
保守的に判定できる条件だけで有効化し、
両面描画や変換で前提が崩れる場合は無効化する。

クラスタごとのGameObject、MeshRenderer、
毎フレームのCPU描画呼び出しを作らない。

本番経路で全クラスタを毎フレームCPU走査して
「GPU駆動」と呼ばない。

GPUで得た描画数を、
同一フレームの同期readbackでCPUへ戻さない。

Geometry Buffer、Instance Buffer、
可視リスト、Indirect Argumentsを使用し、
vertex pulling等で描画する。

描画単位はマテリアルや対応するバッチでまとめ、
クラスタ数に比例するCPU呼び出しを避ける。

異なるマテリアルをどう束ねるか、
未対応プロパティをどう検出するかを明示する。

Graphics.RenderPrimitivesIndirectや
CommandBufferの間接描画APIを候補とし、
実際のRenderGraph実行位置で使える経路を確認する。

グローバルなGraphics API呼び出しを置いただけで、
RenderGraphに資源依存が登録されたと考えない。

描画API側の全体Boundsによって、
内部の可視クラスタまで誤って消されないようにする。

可変長クラスタの扱い、paddingによる空仕事、
バッファ上限、overflow対策を実装する。

overflow時に範囲外アクセスや物体消失を起こさず、
粗い有効表現へ戻すなどの対策を取る。


## 8. HZBオクルージョン

遮蔽判定を無効化した参照モードを常に残す。

通常Z/Reversed Z、背景深度、投影境界、
深度ピラミッドのmin/max規則を明示してテストする。

前フレームのHZBで隠れていたという理由だけで、
今フレームも無条件に捨てない。

カメラ移動、遮蔽物の移動、LOD変更によって
新しく見える領域を同じフレーム内で救済する。

二段階カリングと現在フレーム深度による再判定、
または正しさを説明できる保守的方式を採用する。

カメラのテレポート、解像度変更、投影変更では
履歴を無効化する。

Game ViewとScene View、
複数カメラの履歴を共有しない。

通常のUnityメッシュと本ツールのメッシュが、
実際にどの深度へ書き込むかを確認する。

誤遮蔽による欠落は性能改善より優先して修正する。

不確かな場合は描画する側に倒す。


## 9. ページストリーミング・メモリ管理

ジオメトリデータを独立に読み込めるページへ分割する。

最粗LODと走査に必要な情報を常駐させ、
詳細ページはオンデマンドに読み込む。

常駐階層メタデータ自体の容量も計測し、
無制限に安いものとして扱わない。

GPUから不足ページの要求を出し、
小さな要求バッファを非同期でCPUへ戻す。

要求IDの重複排除、優先度、読み込み中状態、
不要要求の取り消し、再要求を管理する。

CPUは非同期I/Oと必要な展開処理を行い、
フレームごとの上限内でGPUへ転送する。

次の予算を個別に設定できるようにする。

- GPUジオメトリ常駐量
- CPUキャッシュ量
- I/O並列数
- フレームあたり転送量
- 要求キュー上限

メモリ不足時は上限を勝手に拡大せず、
必要な常駐表現を守って詳細度を下げる。

最粗表現すら予算に収まらない場合は、
ロード拒否などの明示的な扱いを行う。

GPU利用中のページを解放・上書きしない。

フレーム遅延、複数カメラ、GPU実行完了、
ページID再利用、ページテーブル更新を考慮する。

必要に応じて世代番号、遅延解放、フェンスを使用する。

ページ未到着時に穴を開けない。

常駐する祖先・粗い置換グループへ戻り、
必要なページ集合がそろってから切り替える。

遅いI/O、要求の集中、破損・欠落ページ、
シーン終了中の読み込みでも
クラッシュしないようにする。

変換後データ全部をScriptableObjectの巨大配列へ
読み込むだけでは、ストリーミング対応としない。

同じメッシュの大量複製だけでは、
ユニークデータがGPU常駐予算を超える検証の
代わりにしない。


## 10. URP、マテリアル、深度、影

URPのRenderGraphを使い、
Compute、Raster、深度生成、描画、
必要なreadbackの順序とRead/Write依存を明示する。

旧APIが必要な場合は対応版で許される境界に限定し、
採用理由と制約を記録する。

最初にUnlitを動かし、
次に専用の不透明Litマテリアルを実装する。

Base Color、Normal、Metallic/Smoothness等は、
実際に実装したものだけ対応表へ記載する。

既存のURP/LitやShader Graphが
無条件に使えると仮定しない。

通常のUnityオブジェクトとの前後関係を確認する。

カメラの深度アタッチメントだけでなく、
後続パスが参照する深度テクスチャへ
結果が反映されるタイミングも検証する。

後続の透明物、深度を使うエフェクト、
DepthOnly/DepthNormals、Depth Primingとの
整合を確認する。

既存プロジェクトのDepth Priming等を
黙って無効化して、対応したことにしない。

影を受ける処理と、影を落とす処理を分ける。

v0.1では対応済みライトの影を受け、
影を落とす用途は生成した低密度Shadow Proxyでもよい。

ただし、
「本ジオメトリからの直接シャドウ」と明確に区別する。

画面に見えるクラスタだけで
影用ジオメトリも十分だと仮定しない。

Collider、Raycast、Editor選択・Pickingは
専用Proxyで対応してよい。

描画形状との精度差を表示し、
巨大な元メッシュを物理用途で常駐させない。

未対応カメラやGPUでは、
理由を表示して通常Renderer/LODへフォールバックする。

フォールバックと専用描画を二重表示しない。


## 11. Editorツールとデバッグ

変換ウィンドウに、対象、設定、推定容量、進捗、
キャンセル、再変換、キャッシュ削除、
通常描画との切り替えを用意する。

変換はUndoや参照復元を考慮し、
元アセットを消さずにやり直せるようにする。

デバッグ表示は少なくとも、
クラスタ色、LOD階層、画面誤差、常駐ページ、
読み込み待ち、カリング理由を
切り替え可能にする。

統計では次を区別する。

- 入力三角形数
- ユニーク三角形数
- インスタンス込み三角形数
- 選択クラスタ数
- 実描画三角形数

さらにGPU/CPU時間、Draw Call、GPU/CPUメモリ、
I/O量、ページミス、品質目標未達、overflowを計測する。

デバッグ可視化の負荷は
通常描画の性能と分けて報告する。


## 12. Omni・対数レンダリングとの接続余地

本体は通常のUnity座標と投影で独立動作させる。

Omniが存在する場合は、
その確定済み座標・投影・深度仕様を調査し、
追加アダプターで接続できるようにする。

標準版完成のために
Omniの実装まで必須にしない。

ローカル頂点、論理位置、カメラ相対位置、
描画位置、LOD評価、深度の責務を分離する。

高精度な論理座標を先にfloatへ落としてから
差分を取る設計を避ける。

変換済みメッシュへ
カメラ依存の対数圧縮を焼き込まない。

対数圧縮後の距離を
通常のLOD距離公式へ入れるだけで済ませない。

実際の投影による画面誤差、
保守的なBounds、カリング、深度、
HZBの整合を検証する。

基準カメラで圧縮した形状を
別のScene Viewから観察する場合は、
描画視点と圧縮基準を混同しない。

変更前後で既存のOmni操作・深度・カリングに
回帰がないことを確認する。


## 13. テスト・性能評価

EditModeで以下をテストする。

入力検証、決定的な変換、階層の非循環性、
領域被覆、誤差管理、量子化境界、
ページ整合、形式互換。

小規模な階層では選択可能なLOD組み合わせを列挙し、
ランダムテストだけで接続保証を済ませない。

描画テストには次を用意する。

平面、球、薄い板、細い柱、穴のあるメッシュ、
鋭い角、UVシーム、複数マテリアル、
境界を持つ地形パッチ。

次の操作・状態を試す。

カメラ接近・遠ざかり・旋回・テレポート、
物体移動、非一様/負スケール、
複数カメラ、ウィンドウリサイズ。

さらに異常系を試す。

遅延I/O、常駐予算不足、要求キューoverflow、
欠損ページ、Play/Stop反復、Domain Reload無効。

CPU参照/GPU実装、
カリングOFF/ON、
全ページ常駐/ストリーミングを切り替えて
差分を比較する。

色だけでなく、
深度、シルエット、欠落領域、LOD境界を確認する。

画像差分の閾値を緩めて
穴を見逃さないようにする。

性能は同じアセット、カメラ軌道、解像度、
マテリアル、影条件で、次を比較する。

- 通常MeshRenderer
- 自動生成LODGroup
- 本ツール

100万、1000万三角形程度から段階的に増やし、
実機容量に応じて調整する。

さらにユニークな変換データ量が
GPUジオメトリ常駐予算を超えるケースを必ず含める。

1080p/60fpsを初期の評価目標としてよいが、
測定前に保証しない。

GPU名、ドライバ、Unity/URP版、Graphics API、
VSync、解像度、メモリ予算を記録する。

平均FPSだけでなく、
CPU/GPUフレーム時間、p95/p99、
メモリ最大値、cold/warm cacheを報告する。

遅くなる場面も残し、
従来方式へ戻す判断条件をまとめる。

GPU描画テストは
実際に描画可能な環境で実行する。

コンパイル成功、
バッチモードのロジックテスト成功、
実画面確認成功を区別する。

実行環境がないテストは「未実施」と記録し、
成功扱いしない。


## 14. 実装順序と合格条件

M0：環境調査と最小描画

実際のURP描画パスで、
バッファ由来の三角形を間接描画する。

通常メッシュとの深度関係を確認する。


M1：変換・クラスタ表示

静的Meshを変換・保存・読み戻しし、
全クラスタを正しく描画する。

元メッシュとの差分を確認する。


M2：階層LOD

CPU参照とGPU実装を作り、
物体内部で詳細度が異なる状態でも
接続と被覆が正しいことを確認する。


M3：GPUカリング

Frustum CullingとHZBを追加し、
高速移動や遮蔽物移動でも
欠落しないことを確認する。


M4：ストリーミング

GPU予算を超えるユニークデータで動かし、
転送制限・遅延・ページ不足でも
粗い表現が維持されることを確認する。


M5：実用化

対応Lit、影/物理/選択Proxy、Scene View、
Editor UI、デバッグ表示、複数カメラ、
ビルド対応、ベンチマークを仕上げる。

M0～M5と本書の必須範囲を満たして初めて
v0.1完成とする。


M6：高度なNanite相当描画

Visibility Bufferとソフトウェアラスタライズを
別段階で実装する。

深度とprimitive IDの一貫した更新、
near clipping、属性復元、UV微分、
通常深度との合成を検証する。

微小三角形と大きな三角形を分担する場合は、
切り替え境界で重複・欠落がないことを確認する。

必要なatomicやGPU機能を実機で検証し、
通常ハードウェア描画より速い条件を
計測してから有効化する。


各段階を動く縦切り実装として完成させ、
段階ごとにコンパイル、テスト、描画確認、
性能測定を行う。

空のクラス、固定値の可視判定、全件可視、
全ページ常駐などを残したまま、
その機能を実装済みと報告しない。

ただし比較・検証用モードとして残すことは認める。


## 15. 納品物と作業規則

納品物は次とする。

ソースコード、UPMパッケージ、
変換Editorツール、Runtime Renderer、
サンプルシーン、自動テスト、
ベンチマーク手順、計測結果、
対応表、制約、再現手順、依存ライセンス一覧。

巨大な生成アセットを不要にGitへ追加せず、
サンプルは小型化または再生成手順で提供する。

Playerビルドに、
不要な高密度元メッシュと変換済みデータが
二重収録されていないか確認する。

既存の未コミット差分を壊さず、
無関係なリファクタリングをしない。

設計案、実装済み、実行確認済み、
未実施を明確に分ける。

性能や品質の数値を作らず、
測定結果と目標値を区別する。

最初に実環境、採用する構成、段階計画、
最大の技術リスクを短く示し、
そのままM0から実装を開始する。

些細な未指定事項は根拠を記録して決定し、
設計相談だけで停止しない。

一度の作業で全段階に達しない場合は、
検証済みの段階、未達条件、
次の具体的な着手点を残す。

途中段階を完成品と偽らない。
